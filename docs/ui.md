# UIの設計と実ブラウザ検証

画面の仕様はアプリのPRODUCT.mdとDESIGN.mdを正本とします。Foundationは共通のUIスタイルを押し付けず、実装と検証の品質を定めます。

## 初期設計：要素を追加する前に

主要タスク、最初に見せる情報、次に進む操作、必要な状態（通常・読込・空・エラー）を先に決めます。文言・装飾・アイコンは、利用者が場所や対象を識別する、判断する、入力・操作する、状態や結果を理解する、失敗やリスクを避ける、のいずれかを助ける場合に採用します。役割を説明できなければ、初期案から省きます。各要素の形式的な台帳は作らず、製品固有の判断だけをDESIGN.mdに記録します。

### 文言と情報

- 見出しは対象、操作ラベルは実行内容、状態表示は実際の状態を短く具体的に伝えます。雰囲気だけのスローガン、意味のない英語の補助見出し、アプリ名を繰り返す説明、仮のコピーを完成画面へ残しません。固有名詞や利用者が使う用語は維持します。
- 同じ内容を見出し・説明・badge・footerで言い換えて重複させません。件数や要約も、作業の優先順位や判断に使うものだけを見せます。日付・単位などの解釈に必要な情報は保ちます。
- 入力例や補助説明は、実際に迷う箇所へ置きます。条件付きで必要な説明はその条件で表示します。空状態は理由と次の操作、エラーは問題と修正方法を伝えます。
- label、accessible name、入力条件、重要な制約、取り消せない操作の確認、データ消失・保存範囲などの説明は、短さを理由に削りません。文字量の削減自体を目標にしません。

### 構成と視覚表現

- 作業用画面では対象データと主操作を先に配置します。heroや大きな紹介文は既定で置かず、製品の理解や訴求が主タスクになる画面で理由を持って採用します。
- 主操作、補助操作、低頻度の操作を区別します。低頻度の設定や詳細は必要に応じて開ける構成にし、現在の条件と解除方法は分かるようにします。頻繁な操作を余計な階層へ隠しません。
- カード・pill・影・gradient・motion・icon boxは、まとまり、状態、操作、ブランドの識別などの役割がある場合に使います。空間を埋めるための要素、対称性のためのKPI、装飾用のステータスは追加しません。
- アイコンは対象や操作の意味が伝わるものを、一貫した既存の体系から選びます。意味の薄い葉・星・任意の文字や記号を仮のブランドマークにしません。ロゴの根拠がなければ明確なアプリ名表示から始めます。独自のブランド表現は製品固有の理由を持って設計します。
- 意味が曖昧なアイコンには見えるラベルを添えます。慣習的なアイコンだけの操作にもaccessible nameを付け、hoverだけを説明の手段にしません。
- 「モダン」は装飾の量ではなく、情報階層、一貫した余白と文字組、読みやすさ、予測できる操作、画面幅に応じた使いやすさで評価します。別アプリの色・ロゴ・配置を成功例という理由だけで強制しません。

## 実装

1. 初期設計の採用判断とDESIGN.mdを確認し、テンプレートや部品デモの文言・構成をそのまま製品へ持ち込みません。
2. セマンティックHTMLと成熟したアクセシブルなUIプリミティブを優先します。ReactアプリではTailwind CSSとshadcn/ui相当の基本部品が既定候補ですが、プロダクトの制約に従います。
3. プリミティブ品質と画面構成を区別します。前者はlabel、focus、keyboard、disabled/error、hit area、dialog等の振る舞い、後者は情報の優先順位、グループ化、文字組、余白、密度、タスク導線です。
4. 画面構成はDESIGN.mdに記録した目的で判断します。「モダンなSaaS」「premium」「clean」といった抽象語だけで設計を正当化しません。
5. 日本語の長いラベル、日付、数値、単位、省略、改行、スクリーンリーダーの読み順を考慮します。不要なカード・装飾・情報の二重表示は増やしません。

## 実ブラウザ検証

ソース確認、Lint、型チェック、build、HTTP 200は実際の視覚的・操作的な成立の証拠にはなりません。重要なUI変更では実装そのものをChromium/Playwrightなどでレンダリングします。

- 目安として320px／390px／1440pxで表示し、横はみ出し・文字の重なり・日本語の不自然な折り返し、情報の優先順位と読み順を確認します。
- Tab／Shift+Tab／Enter／Escape等、機能に必要なキーボード動作を確認し、**実際に見えるfocus indicator**を検査します。
- 画面の必須見出し・状態・操作に対応するselectorは、対象要素が0件の場合に失敗させます。状態遷移と期待テキストを検証します。
- ローディング・未観測・エラー・権限不足など、アプリが想定する現実の状態を確認します。「API成功」のみで表示を成功扱いにしません。
- 操作前にpageerrorとconsole.errorを捕捉します。非同期UIはlocator assertion／expect.pollで有限timeout内の期待状態を待ちます。固定sleepやnetworkidleだけで準備完了としません。停止状態は時計制御やstep数などで実際の観測区間を検査します。
- 成功時にも3画面幅の画像を保存し、日本語の折返し・数値入力・重なりを目視します。テスト失敗時のスクリーンショット・traceを期限付きArtifactに保存します。センサー情報、個人情報、Token、Cookieを不用意に出力しません。
- 各スクリーンショットが検証したコミット・URL・viewport・テストrunと関連付いていることを確認します。

既定のE2Eは軽量な代表シナリオから始めます。全ブラウザ/全viewportの組合せ、大規模なvisual regressionサービス、常時起動のブラウザ環境は必要性を確認してから導入します。

## 最終レビュー

意図した体験と実際の画面を見比べ、初期設計と同じ採用基準で確認します。

- 初見で対象・現在の状態・次の操作が分かるか。
- 実際に表示された文言・装飾・アイコンに役割があり、仮のコピーや重複表示が残っていないか。
- 補助情報の開閉後も現在の条件が分かり、主操作へ無駄なく到達できるか。
- 説明を省いたことで入力、状態、制約、安全性、アクセシビリティが曖昧になっていないか。

ブラウザ環境が使えない場合はCIや承認済みSandboxを検討し、それでも不可能なら未検証と報告します。GitHubのCI greenやPreview READYとは分けて扱います。

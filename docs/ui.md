# UIの設計と実ブラウザ検証

画面の仕様はアプリのPRODUCT.mdとDESIGN.mdを正本とします。Foundationは共通のUIスタイルを押し付けず、実装と検証の品質を定めます。

## 実装

1. 主要タスク、最初に見せる情報、次に進む操作、必要な状態（通常・読込・空・エラー）を確認します。
2. セマンティックHTMLと成熟したアクセシブルなUIプリミティブを優先します。ReactアプリではTailwind CSSとshadcn/ui相当の基本部品が既定候補ですが、プロダクトの制約に従います。
3. プリミティブ品質と画面構成を区別します。前者はlabel、focus、keyboard、disabled/error、hit area、dialog等の振る舞い、後者は情報の優先順位、グループ化、文字組、余白、密度、タスク導線です。
4. 画面構成はDESIGN.mdに記録した目的で判断します。「モダンなSaaS」「premium」「clean」といった抽象語だけで設計を正当化しません。
5. 日本語の長いラベル、日付、数値、単位、省略、改行、スクリーンリーダーの読み順を考慮します。不要なカード・装飾・情報の二重表示は増やしません。

## 実ブラウザ検証

ソース確認、Lint、型チェック、build、HTTP 200は実際の視覚的・操作的な成立の証拠にはなりません。重要なUI変更では実装そのものをChromium/Playwrightなどでレンダリングします。

- 目安として320px／390px／1440pxで表示し、横はみ出し・文字の重なり・日本語の不自然な折り返し、情報の優先順位と読み順を確認します。
- Tab／Shift+Tab／Enter／Escape等、機能に必要なキーボード動作を確認し、**実際に見えるfocus indicator**を検査します。
- 画面の必須見出し・状態・操作に対応するselectorは、対象要素が0件の場合に失敗させます。状態遷移と期待テキストを検証します。
- ローディング・未観測・エラー・権限不足など、アプリが想定する現実の状態を確認します。「API成功」のみで表示を成功扱いにしません。
- 操作前にpageerrorとconsole.errorを捕捉します。非同期UIはlocator assertion／expect.pollで有限timeout内の期待状態を待ちます。固定sleepやnetworkidleだけで準備完了としません。停止状態は時計制御やstep数などで実際の観測区間を検査します。
- 成功時にも3画面幅の画像を保存し、日本語の折返し・数値入力・重なりを目視します。テスト失敗時のスクリーンショット・traceを期限付きArtifactに保存します。センサー情報、個人情報、Token、Cookieを不用意に出力しません。
- 各スクリーンショットが検証したコミット・URL・viewport・テストrunと関連付いていることを確認します。

既定のE2Eは軽量な代表シナリオから始めます。全ブラウザ/全viewportの組合せ、大規模なvisual regressionサービス、常時起動のブラウザ環境は必要性を確認してから導入します。

## 最終レビュー

意図した体験と実際の画面を見比べ、主要タスクが読み取りやすく操作可能かを判定します。ブラウザ環境が使えない場合はCIや承認済みSandboxを検討し、それでも不可能なら未検証と報告します。GitHubのCI greenやPreview READYとは分けて扱います。

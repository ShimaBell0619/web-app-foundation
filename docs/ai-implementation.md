# Chat・WorkによるAI開発

`AGENTS.md` を前提に、**Chatを標準の実行オーケストレーター**とする。目的から必要な道具を選び、実装・検証・デプロイ・後片付け・報告を進める。**Workはユーザーが明示指示した場合に限る。** 道具の不足、作業量、ブラウザ操作の必要性から自動的にWorkへ移行しない。

## 基本フロー

```text
Chat：依頼を理解し、受け入れ条件と承認境界を確認
  ↓ 既存の仕様・実装・利用可能な道具を調査
Chat：直接ツール／実行環境／Sandbox／信頼済みWorkflowを選択
  ↓ Issue（必要な場合）→ ブランチ → 変更 → CI/実行/画面の検証
Chat：結果を検証し、必要なら修正 → 再検証
  ↓ PR・マージ・承認済みデプロイ・スモーク・後片付け
Chat：各段階の証拠と残存リスクを報告
```

## ChatとWorkの選択

| 作業 | Chatからの第一候補／代替 |
| --- | --- |
| 要件・設計・Issue・PR・コミット | GitHub接続ツール。複数ファイルはGit Tree/Commitを使う |
| テスト・ビルド | Chat実行環境。不可ならGitHub Actionsの品質ゲート |
| 実画面・レスポンシブ・キーボード | PlaywrightをCI・一時実行環境で実行し、HTMLではなく実ブラウザ証拠を取得 |
| Vercel/配備と診断 | Vercel接続ツール、ビルド・実行ログ、必要なら一時Sandboxから疎通 |
| Azureリソース操作 | 直接利用できる承認済み接続、またはGitHub Actions + OIDC + Azure CLI/Bicep |
| GitHub repo作成・ブランチ削除 | 直接ツールが無ければ最小権限の管理Workflow。未整備なら必要な初期設定を明記 |
| Work | **ユーザーから明示的に指定された場合のみ** |

### Chatの実行経路の選択

1. **直接ツール**：利用可能なコネクターの操作スキーマと権限を確認。読み取り・書き込み・削除を混同しない。
2. **Chat内実行**：ローカルのコード実行、テスト、ファイル解析。外部ネットワーク・ブラウザが利用できるとは仮定しない。
3. **一時実行環境**：接続済みVercel Sandbox等で必要なコマンドを実行。対象ドメイン制限、短いタイムアウト、最小限の権限、停止処理を行う。継続課金のある変更には承認を要する。
4. **既存の信頼済みWorkflow**：Issueコメント等、ツールから実際に起動できるトリガーで品質ゲートやオーナー承認付き操作を実行する。実行者/PR/SHA/対象リソースを再検証し、操作後の結果を記録する。
5. **対応する経路がない場合**：ない権限や初回接続・操作準備を具体的に説明し、実行不能な工程を未完了として残す。Workへ自動移行せず、架空の代替実行を主張しない。

実行ルートは順に全て試す義務ではなく、最小リスク・コスト・手戻りで目的と検証を満たすものを選ぶ。**経路を切り替えても認証、許可された権限、課金同意、承認、監査を迂回しない。** ブラウザ画面が要件なのにHTTP 200や静的モックだけで代用しない。

### GitHub・Azure操作の安全な委譲

- GitHubブランチ削除：直接削除できない場合、保護対象や`main`を除外し、PRマージ済み・対象HEAD一致・許可された短命ブランチであることを確認してから管理Workflowで削除。force push・予期しないref削除は禁止。
- GitHubリポジトリ作成：既存リポジトリがないため既存の専用管理リポジトリを起点とし、スコープを限定した認証・許可済み所有者・重複確認・可視性・テンプレート・初期設定を検証。初回権限設定はChatから勝手に代替できない。owner-wideトークンをPRに渡さない。
- Azure：読み取り、What-if、変更、削除を区別し、実行対象のSubscription/RGとRBACを確認。GitHub OIDCによる既存の専用Workflowを優先し、任意のコマンド文字列をPRコメントから特権付きシェルへ渡さない。
- 書き込みと検証は別のフェーズ。権限のあるWorkflowで未信頼PRコードを実行しない。秘密情報やOIDCトークンをChat/PR/ログへ表示しない。成果物・実行ID・各段階の成功可否を残す。

## 着手前に確認すること

1. Issueまたは依頼の目的、受け入れ条件、変更しない既存動作を把握する。小規模な作業に長い計画書は不要。
2. `PRODUCT.md`、`AGENTS.md`、必要な `DESIGN.md`・専門文書を読む。変更対象外の文書を網羅的に読み込まない。
3. 実装とテストの既存構造を確認し、どこを変更すれば目的を満たすかを特定する。
4. 仕様同士の矛盾、認可・課金・公開・データ消去など未承認の重要判断があれば、書き込み前に相談する。
5. ベースSHAを確認し、作業ブランチを作成する。GitHubの変更を上書きせず、競合を検知する。

### 必要な文脈だけを選ぶ

- 製品仕様：`PRODUCT.md`
- 画面やUX：`DESIGN.md`、`docs/ui-implementation.md`、`docs/ui-review.md`
- 実運用・配備：対象のVercel／Release／Azure連携文書
- Foundation導入・更新：`docs/adoption.md` と採用元のコミット

この分類は探索の目安であり、変更の影響が広がったら参照先も追加する。永続的なContext Packet、独自エージェント基盤、キャッシュ管理ファイルは作らない。

## ChatからWorkへ引き継ぐ情報

**Workへ渡すのはユーザーがWorkを明示的に指定した場合だけ**。同じ項目はChat内の一時実行環境やGitHub Workflow間の実行引き継ぎにも使用できる。GitHub IssueまたはPRに、必要な範囲で以下を残す。

- **目的**：何を改善するか
- **受け入れ条件**：何を観測すれば完了か
- **制約・非対象**：何を維持し、何をしないか
- **設計判断**：承認済みの重要な選択と関連文書
- **作業状態**：ブランチ、HEAD SHA、未完了事項、テスト結果（存在する場合）

会話全文や内部推論を転記しない。実装担当は引き継ぎ内容と現在のGitHub状態を照合し、古いSHA・CI証拠をそのまま信じない。

## 実装と検証

1. 受け入れ条件を満たす最小の実装を行い、必要な回帰テストを追加する。
2. 変更した対象に絞ったテストを実施し、実質的な修正後に最終の品質ゲートを実行する。
3. 最終差分を第三者の立場で自己レビューし、要求との食い違い、既存動作への影響、エラー処理、セキュリティ、過剰な抽象化を点検する。
4. 指摘があれば修正・再確認し、最終版に対して検証をやり直す。意味のない再修正や確認のループは不要。
5. UI変更はPlaywrightなどで実装そのものを実ブラウザで確認する。手元でブラウザが動かなければ、まずCIや一時Sandboxを検討する。実施できない場合は未検証として報告する。**Workに自動移行しない。**

**Chat + GitHubでの注意：** GitHub Actionsの成功は、そこで実行されたチェックだけを証明する。ブラウザ表示・外部サービス連携など、CIで確認していない事項を検証済みとは言わない。CI実行前に完成を宣言しない。

## PRと独立レビュー

PRには目的、主要変更、受け入れ条件と証拠、最終検証、残るリスクを簡潔に記載する。作業途中の試行錯誤や会話ログは不要。

自己レビューとCIは必須の品質確認。独立レビューは高リスクの変更に限って判断する。Codex GitHub Code Reviewの実行・再実行には、その都度理由を説明し明示的な承認を得る。詳しくは `docs/independent-review.md` を参照する。

## 完了報告

変更したファイルやPR、テスト・CIの結果、実行していない検証、重要な残存リスクをまとめる。完了条件が満たせない場合は、未完了と明示する。

## 過剰な複雑化を防ぐ

新しいレイヤー、Skill、Subagent、外部サービス、ワークフロー、恒久的な資料を、将来の可能性だけで増やさない。明確に繰り返される作業や実在する責務境界が見えたときに、最小限の仕組みを追加する。安全性・復旧性を削ることは単純化ではない。

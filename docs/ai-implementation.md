# Chat・WorkによるAI開発

`AGENTS.md` の共通ルールを前提に、Chat + GitHubを標準とし、実行環境が必要なときだけWorkへ切り替えるための手順を定める。コーディングツールの違いは仕様・品質・承認条件を変えない。

## 基本フロー

```text
依頼・Issue
  ↓ Chat：要件と受け入れ条件の整理、設計判断
GitHub Issue（または合意済みの短い変更指示）
  ↓ ChatまたはWork：対象仕様と実装の確認
作業ブランチ → 実装 → テスト → 自己レビュー
  ↓ 必要に応じてWorkで実行・画面検証
PR・CI・最終差分の確認
  ↓ 高リスク変更のみ独立レビューを検討
承認・マージ
```

## ChatとWorkの選択

| 作業 | 第一候補 |
| --- | --- |
| 要件整理・設計比較・受け入れ条件 | Chat |
| GitHub上の調査、文書変更、小〜中規模の修正 | Chat + GitHub |
| ビルド、単体テスト、E2E、ブラウザでの表示確認 | Work、またはGitHub Actionsで実行できる範囲 |
| 大量のコード変更、実行を伴う試行錯誤 | Work |
| 最終的な設計適合性・リスク判断 | ChatとGitHubのPR・CI証拠 |

役割を固定しすぎない。Chatで作業を始めても実行検証が必要になればWorkへ移す。WorkからChatへ戻す場合はIssue・PR・コミット・検証結果を引き継ぐ。

## 着手前に確認すること

1. Issueまたは依頼の目的、受け入れ条件、変更しない既存動作を把握する。小規模な作業に長い計画書は不要。
2. `PRODUCT.md`、`AGENTS.md`、必要な `DESIGN.md`・専門文書を読む。変更対象外の文書を網羅的に読み込まない。
3. 実装とテストの既存構造を確認し、どこを変更すれば目的を満たすかを特定する。
4. 仕様同士の矛盾、認可・課金・公開・データ消去など未承認の重要判断があれば、書き込み前に相談する。
5. ベースSHAを確認し、作業ブランチを作成する。GitHubの変更を上書きせず、競合を検知する。

### 必要な文脈だけを選ぶ

- 製品仕様：`PRODUCT.md`
- 画面やUX：`DESIGN.md`、`docs/ui-implementation.md`、`docs/ui-review.md`
- 実運用・配備：対象のVercel／Release／Azure連携文書
- Foundation導入・更新：`docs/adoption.md` と採用元のコミット

この分類は探索の目安であり、変更の影響が広がったら参照先も追加する。永続的なContext Packet、独自エージェント基盤、キャッシュ管理ファイルは作らない。

## ChatからWorkへ引き継ぐ情報

GitHub IssueまたはPRに、必要な範囲で以下を残す。

- **目的**：何を改善するか
- **受け入れ条件**：何を観測すれば完了か
- **制約・非対象**：何を維持し、何をしないか
- **設計判断**：承認済みの重要な選択と関連文書
- **作業状態**：ブランチ、HEAD SHA、未完了事項、テスト結果（存在する場合）

会話全文や内部推論を転記しない。実装担当は引き継ぎ内容と現在のGitHub状態を照合し、古いSHA・CI証拠をそのまま信じない。

## 実装と検証

1. 受け入れ条件を満たす最小の実装を行い、必要な回帰テストを追加する。
2. 変更した対象に絞ったテストを実施し、実質的な修正後に最終の品質ゲートを実行する。
3. 最終差分を第三者の立場で自己レビューし、要求との食い違い、既存動作への影響、エラー処理、セキュリティ、過剰な抽象化を点検する。
4. 指摘があれば修正・再確認し、最終版に対して検証をやり直す。意味のない再修正や確認のループは不要。
5. UI変更は画面を実際にレンダリングして確認する。実行環境がない場合はWorkへ移すか、未検証として報告する。

**Chat + GitHubでの注意：** GitHub Actionsの成功は、そこで実行されたチェックだけを証明する。ブラウザ表示・外部サービス連携など、CIで確認していない事項を検証済みとは言わない。CI実行前に完成を宣言しない。

## PRと独立レビュー

PRには目的、主要変更、受け入れ条件と証拠、最終検証、残るリスクを簡潔に記載する。作業途中の試行錯誤や会話ログは不要。

自己レビューとCIは必須の品質確認。独立レビューは高リスクの変更に限って判断する。Codex GitHub Code Reviewの実行・再実行には、その都度理由を説明し明示的な承認を得る。詳しくは `docs/independent-review.md` を参照する。

## 完了報告

変更したファイルやPR、テスト・CIの結果、実行していない検証、重要な残存リスクをまとめる。完了条件が満たせない場合は、未完了と明示する。

## 過剰な複雑化を防ぐ

新しいレイヤー、Skill、Subagent、外部サービス、ワークフロー、恒久的な資料を、将来の可能性だけで増やさない。明確に繰り返される作業や実在する責務境界が見えたときに、最小限の仕組みを追加する。安全性・復旧性を削ることは単純化ではない。

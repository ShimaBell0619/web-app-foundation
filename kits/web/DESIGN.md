# Design System

## Overview

この文書は共通のデザイン基準です。アプリの `DESIGN.md` へコピーし、name／description、具体的なtoken、説明を製品固有の内容に置き換えてください。生成だけではデザイン承認済みとしません。

UI・UXの判断はこの文書、製品の動作は `PRODUCT.md`、開発規則は `AGENTS.md` に記載します。大きな技術構成は実在する専門文書へ分離します。

Google DESIGN.md alphaの[固定仕様](https://github.com/google-labs-code/design.md/blob/9bf8eae67128b6cc55ad9bf86665767deb4c11cd/README.md)（release 0.4.0）に合わせ、front matterのキーと標準section見出しは英語を維持します。説明は日本語です。schema更新時は固定仕様を再確認し、翻訳と機械契約変更を混ぜません。

利用者の作業を起点に、明確な階層、予測できる操作、アクセシブルな部品、必要な視覚的複雑さを選びます。大きなUI実装前に、製品の作業・データ・流れに結び付くデザイン方針を一文で定義します。「モダンなSaaS」のような見た目だけの説明では不十分です。

主要作業、第一に見せる情報と補助情報、色と文字の役割、カードなどの囲いの理由、狭い画面での優先順位、アクセシビリティ、避ける汎用パターンと理由を必要に応じて明示します。別アプリの配色・角丸・書体・装飾・画面構成は、そのアプリで成功したという理由だけでコピーしません。

実装部品と製品の視覚的な個性は別の責務です。共通部品の実装方針は採用元のUI手順を参照し、情報階層、構成、tokenの意味、書体、密度の正本はこの文書に保ちます。

## Colors

- 色の値を散在させず、意味を持つ役割を定義します。
- 文字、アイコン、操作部品、focus、状態表示のコントラストを確保し、色だけで意味を伝えません。
- light／dark／systemは明示的に選択します。アクセント、gradient、glowにも製品・階層上の理由を持たせます。
- 製品固有のtokenはこの文書と実装のthemeへ記録します。

## Typography

- 見出し、本文、ラベル、補助情報、識別子、日付などの役割に応じた少数の文字階層を定義します。
- 読みやすい行長と文字サイズを選び、zoomと文字拡大を尊重します。ほぼ同じスタイルを増やしません。
- 実際の長文を描画して、切れ・不自然な折返しを確認します。日本語／CJKでは対象環境のfallback書体も確認します。
- 書体とtoken値をこの文書へ記録します。

## Layout

- 主な作業と情報階層から構成を決めます。同じ大きさのカードや列を対称性だけで強制しません。
- 実際のviewport／container幅を基準にし、短い内容を大画面へ引き伸ばしません。
- 狭い画面でも重要操作に到達できる密度を保ち、横overflowを防ぎます。
- 余白の体系ができたらtokenを使います。touch、pointer、keyboard、ウィンドウ変更を対象にします。
- 幅が足りないときに何が先に縮み、並び替わり、折り返し、非表示になるか定義します。

## Elevation & Depth

- 強い影より、面の階層、境界、余白、コントラストを優先します。
- 高さは重なりや操作を伝えるために使います。overlay、popover、dialog、sticky領域を背景と区別します。
- 各情報を独立した面にするのではなく、囲いがまとまりや操作を明確にする場合に使います。

## Shapes

- 少数の一貫した角丸を使い、部品の役割や製品の個性に結び付けます。同じ役割の形を無理由で変えません。
- pill、柔らかなicon box、円、badgeは役割・状態・操作・製品上の意味がある場合に使います。

## Components

- semantic HTMLと標準のアクセシブルな動作を優先します。Reactの通常部品はTailwind CSSとshadcn/ui相当の成熟した基本部品を既定にします。
- 汎用部品に製品ドメインの意味を混ぜません。製品固有の共通部品は実際の反復か恒常的な操作規則がある場合に作ります。
- 製品の個性は階層、構成、書体、意味を持つ色、密度、データ表示、操作の流れで作ります。通常操作を独自に再発明しません。
- 特殊な可視化や操作に利点があれば固有CSSを使います。
- keyboard、見えるfocus、label／accessible name、エラーとの関連、操作対象サイズを保ちます。
- 必要なloading、empty、error、disabled、selected、successを設計します。進捗は意味のある完了率を持つ場合だけ表示します。
- 同じ状態・KPI・日付・識別子を空間埋めのために重複させず、製品コードを根拠のない紋章やbadgeにしません。

## Do's and Don'ts

### Do

- 主な作業と操作を明確にし、視覚的な重みをデータ・作業・階層・アクセシビリティで説明します。
- 等分KPI、反復カード／pill、柔らかなicon box、装飾gradient／glow／orb、大文字の補助見出し、番号付きsectionはレビューの手掛かりとして扱います。自動的な正解・違反にはしません。
- 重要なUI変更は描画→批評→修正→再描画で確認します。1440／390／320pxを基準に、製品の境界条件を追加します。
- overflow、長文、keyboard／focus、状態の意味、日本語の折返しとfallbackを実画面で確認します。
- tokenで実装を一貫させ、可能ならprogressive enhancementを使います。標準section順序を維持します。

### Don't

- 製品要件、release方針、詳細な技術構成をこの文書へ混ぜません。
- 必要性のない独自design system、装飾目的だけのmotion・影・gradient・glass・card・pill・icon box・情報密度を導入しません。
- 「モダンなdashboard」だけを根拠にせず、汎用パターンを機械的に禁止もしません。役立つパターンは製品の理由を持って使います。
- 部品ライブラリのデモ構成や別vendorの見た目を製品の情報構成として転用しません。
- 必須操作をhoverだけに隠しません。desktop一枚だけでresponsive確認済みとしません。
- 通常のAI実装に外部デザインファイルだけを必須正本としません。

共通の実装・描画レビュー手順は採用元のUI文書を参照してください。Google DESIGN.mdはalphaです。機械可読front matterとレビュー済みschemaを保ち、未対応の重要な判断は独自キーでなくMarkdown本文へ記載します。
